# Проксирование запросов через Nginx

История о том, как задача на 5 минут вылилась в несколько дней изучений, и какие технические детали я из этого вынес.

Сама задача максимально простая — добавить кнопку скачивания файла. Однако, при вызове эндпоинта в ответ приходит `400 Bad Request. Invalid HTTP request received`.

Довольно быстро стало понятно, что проблема находится на стороне фронтового Nginx, который проксирует запросы, и связана она с наличием русских символов в строке запроса, а точнее с их кодированием (нормализацией) и декодированием.

Сразу оговорюсь: я не специалист по Nginx. В большинстве проектов мне хватало базовых конфигураций и готовых примеров.

Порывшись в официальной документации Nginx, различных статьях и LLM, вот к чему я пришёл:

При отправке запроса, например такого `/api/service/download/акт_2026.pdf`, браузер автоматически (можно и руками) нормализует все недопустимые символы. В итоге строка запроса превращается в `/api/service/download/%D0%B0%D0%BA%D1%82_2026.pdf`.

Далее запрос приходит на Nginx, где выбирается подходящий (в моём случае, по регулярному выражению) location.

```nginx
location ~* /api/service/(.*) {
  set $target_host ${SERVICE_ADDR};
  proxy_pass $target_host/api/$1$is_args$args;
}
```

Для контекста: вместо шаблона `${SERVICE_ADDR}` подставляется адрес бекенд сервиса, куда будет проксироваться запрос.

Регулярное выражение применяется к встроенной `$uri` переменной, в которой строка запроса уже декодирована (`/api/service/download/акт_2026.pdf`), в итоге в переменную `$1` захватывается `download/акт_2026.pdf`. Оно же и подставляется в директиву `proxy_pass`. Тут важно запомнить, что при таком формировании `proxy_pass`, Nginx не нормализует строку обратно. В итоге, запрос проксируется как `/api/download/акт_2026.pdf`, что и приводит к ошибке.

Интересный нюанс: если использовать `$1` в промежуточной переменной

```nginx
set $path /api/$1;
proxy_pass $backend_host$path$is_args$args;
```

`proxy_pass` отработает корректно, т.к. `$path` будет содержать `/api/download/%D0%B0%D0%BA%D1%82_2026.pdf`.

Вообще, самый простой и рабочий вариант проксирования выглядит вот так:

```nginx
location /api/service/ {
  proxy_pass ${SERVICE_ADDR}/api/;
}
```

Однако, тут есть нюанс. При указании хоста непосредственно в `proxy_pass`, его резолвинг происходит в момент запуска Nginx, и если по какой-то причине этот процесс вернёт ошибку (например, в данном окружении нет такого сервиса), Nginx выбросит исключение. А вот хост записанный в переменную (как в изначальном примере) резолвится в момент обработки запроса.

Есть ли вариант настроить проксирования без регулярного выражения в `location` (так как оно медленнее) и без дополнительной переменной? Да, их как минимум два.

### Вариант с использованием $request_uri:

```nginx
location /api/service/ {
  rewrite ^ $request_uri;
  rewrite ^/api/service/(.*)$ $1 break;
  proxy_pass $backend_host/api/$1;
}
```

Ещё одна встроенная переменная `$request_uri` содержит оригинальную (нормализованную) строку запроса с аргументами.

Обратите внимание: при использовании `$request_uri` в сочетании с переменными `$1…9` можно случайно получить двойную нормализацию на выходе, в результате чего запрос превратится в `/api/download/%25D0%25B0%25D0%25BA%25D1%2582_2026.pdf`.

### Вариант с простым rewrite:

```nginx
location /api/service/ {
  rewrite ^/api/service/(.*)$ /api/$1 break;
  proxy_pass $backend_host;
}
```

В данном случае, директива `rewrite` перезаписывает значение `$uri` переменной. И так как в `proxy_pass` мы указали только хост, Nginx сам собирает строку из `$uri`, попутно нормализуя её, и `$args`.
